## 一、核心攻击面与漏洞类型

### 1. 签名验证类漏洞
- **None 算法攻击（CVE-2015-9235）**：将 header 中 `alg` 改为 `none`，移除签名部分，利用服务端未校验算法白名单的缺陷绕过认证
- **未验证签名**：服务端仅调用 `decode()` 解析 payload，完全跳过签名校验，任意伪造 token 均可通过
- **算法混淆攻击（RS256 → HS256）**：服务端同时支持对称与非对称算法时，攻击者用公钥作为 HMAC 密钥伪造签名
- **弱密钥爆破**：HS256 等对称算法使用弱密钥时，可通过 hashcat、jwt_tool 等工具字典爆破密钥

### 2. Header 参数注入类
- **JWK 头注入**：服务端信任 token 中 `jwk` 字段携带的公钥，攻击者注入自定义密钥对伪造签名
- **JKU 头注入**：`jku` 指向攻击者可控的 JWKS URL，服务端从恶意地址拉取公钥验证
- **kid 头注入**：`kid`（密钥ID）参数未过滤，可导致路径遍历、SQL注入、SSRF 或读取任意文件
- **x5u/x5c 证书注入**：服务端信任 token 中携带的证书链，攻击者使用自签名证书

### 3. Claims 校验缺失
- **exp 过期时间未校验**：已过期令牌仍可正常使用
- **nbf/iat 未校验**：令牌可在生效时间前使用，或未来签发的伪造令牌被接受
- **iss 签发者未校验**：接受非信任来源签发的令牌
- **aud 受众未校验**：跨服务令牌滥用，A 服务令牌可访问 B 服务
- **scope 权限未校验**：低权限令牌可执行高权限操作

### 4. 密钥管理缺陷
- 密钥硬编码在代码、配置文件或环境变量中泄露
- 密钥强度不足（长度 < 256 位）
- 长期不轮换密钥
- 多服务共用同一密钥
- 私钥泄露（非对称算法场景）

### 5. 传输与存储风险
- HTTP 明文传输导致中间人窃取
- 前端存储于 localStorage/sessionStorage，易被 XSS 窃取
- URL 参数传递令牌，泄露至日志、浏览器历史、Referer
- Refresh Token 未设置 HttpOnly、Secure 属性

## 二、安全加固最佳实践

### 1. 算法与签名安全
- **强制算法白名单**：服务端硬编码指定允许的算法，绝不信任 header 中的 `alg` 字段
- **优先非对称算法**：推荐 RS256、ES256，避免 HS256 对称算法（密钥分发风险高）
- **禁止混合算法**：同一服务不同时启用对称 + 非对称算法，防止算法混淆攻击
- **禁用 none 算法**：显式拒绝 `alg: none` 的令牌
- **签名强度**：至少使用 SHA-256 及以上哈希，禁用 HS1、MD5 等弱算法

### 2. 密钥管理规范
- **密钥强度**：HMAC 对称密钥至少 256 位随机字符串；RSA 至少 2048 位，推荐 4096 位；ECDSA 使用 P-256 曲线
- **密钥存储**：使用 KMS 密钥管理服务或加密的环境变量，禁止硬编码
- **密钥轮换**：建立定期轮换机制，轮换期间新旧密钥并行兼容
- **kid 安全**：`kid` 仅用于索引预定义密钥列表，禁止直接拼接文件路径或 SQL 查询
- **非对称场景**：私钥严格离线保管，公钥可通过受信任 JWKS 端点分发

### 3. Claims 强制校验
| 声明 | 校验要求 | 安全作用 |
|------|----------|----------|
| `exp` | 当前时间必须早于过期时间，允许几秒时钟漂移 | 防止过期令牌滥用 |
| `nbf` | 当前时间必须晚于生效时间 | 防止令牌提前使用 |
| `iat` | 校验签发时间合理性，拒绝未来时间签发 | 检测伪造令牌 |
| `iss` | 必须与预期签发者完全一致 | 确保令牌来源可信 |
| `aud` | 必须包含当前服务标识 | 防止跨服务滥用 |
| `sub` | 校验用户身份合法性 | 确认主体身份 |
| `jti` | 结合黑名单实现令牌撤销、防重放 | 一次性令牌校验 |
| `scope` | 校验权限范围与操作匹配 | 权限粒度控制 |
| `typ` | 校验令牌类型（如 `at+jwt`） | 区分访问令牌与ID令牌 |

### 4. 令牌生命周期管理
- **Access Token**：有效期 15 分钟 ~ 1 小时，遵循最短有效期原则
- **Refresh Token**：有效期 7 ~ 30 天，单次使用即失效（轮换机制）
- **令牌撤销**：实现基于 jti 的黑名单机制，支持主动登出
- **刷新限流**：对刷新接口设置速率限制，防止暴力滥用
- **并发刷新防护**：处理多请求并发刷新场景，避免重复生成

### 5. 传输与存储安全
- **强制 HTTPS**：全站启用 HTTPS，配置 HSTS 头防止降级攻击
- **Cookie 存储**：Refresh Token 使用 HttpOnly + Secure + SameSite=Strict/Lax Cookie
- **内存存储**：Access Token 前端仅存内存中，不持久化
- **禁止 URL 传递**：令牌必须放在 Authorization 请求头中
- **CORS 严格配置**：限制允许的源站、方法和头部

### 6. Header 参数防护
- 忽略 token 中的 `jwk`、`x5u`、`x5c` 字段
- `jku` 仅允许访问白名单内的可信域名
- 对 `kid` 参数进行严格白名单校验或格式校验
- 拒绝包含未识别关键参数的令牌

## 三、渗透测试检查清单

### 1. 基础信息收集
- 解码 JWT，分析 header 与 payload 字段
- 识别签名算法类型
- 检查是否包含敏感信息（密码、手机号等）
- 确认令牌各声明字段完整性

### 2. 签名绕过测试
- 修改 payload，保留原签名 → 验证是否校验签名
- `alg: none` 攻击 → 移除签名部分重放
- 空签名测试 → 签名部分留空
- 算法切换测试 → HS256 ↔ RS256 互换

### 3. 密钥强度测试
- 使用常见字典爆破 HS256 密钥
- 搜索代码仓库、配置文件中的硬编码密钥
- 测试密钥长度是否符合安全标准

### 4. Header 参数测试
- 注入 `jwk` 自定义密钥
- 注入 `jku` 指向恶意 JWKS 地址
- `kid` 参数测试路径遍历（`../../etc/passwd`）、SQL注入、SSRF
- 测试 `x5u`、`x5c` 证书注入

### 5. Claims 校验测试
- 修改 `exp` 为过去时间 → 测试是否接受过期令牌
- 修改 `exp` 为极远未来 → 测试是否有最大有效期限制
- 修改 `nbf` 为未来时间 → 测试是否生效
- 篡改 `iss`、`aud` → 测试是否校验来源与受众
- 跨服务令牌复用测试

### 6. 业务逻辑测试
- 令牌撤销后是否仍有效
- Refresh Token 是否可重复使用
- 越权测试：修改用户ID、角色、权限字段
- 令牌泄露场景：日志、Referer、URL 参数

## 四、安全验证流程标准
完整的 JWT 验证八步流程：
1. **格式校验**：三段式结构、Base64Url 编码合法性
2. **算法校验**：`alg` 在服务端白名单内
3. **密钥获取**：根据 `kid` 从可信来源获取密钥
4. **签名验证**：使用指定算法和密钥校验签名完整性
5. **时间校验**：exp、nbf、iat 时间窗口验证
6. **身份校验**：iss、aud 签发者与受众匹配
7. **权限校验**：scope / 角色与请求操作匹配
8. **业务校验**：用户状态、令牌撤销状态检查

## 五、高危红线（必须禁止）
- ❌ 禁止不验证签名直接解析 payload
- ❌ 禁止使用 `none` 算法
- ❌ 禁止在 JWT payload 中存放敏感信息（密码、密钥、身份证号等）
- ❌ 禁止对称与非对称算法同时启用
- ❌ 禁止信任 token 中携带的公钥/证书
- ❌ 禁止长期有效令牌（超过 24 小时的 Access Token）
- ❌ 禁止 HTTP 明文传输令牌
- ❌ 禁止将 Refresh Token 存入 localStorage
